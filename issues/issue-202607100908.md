# 課題解決プロンプト: org-toolkit コード品質レビュー：未熟・設計不備箇所の是正

## 1. 役割定義 (Persona)
あなたは高度なソフトウェアエンジニアおよび問題解決のエキスパートです。以下のコンテキストとゴールを基に、正確かつ効率的な修正/実装を行ってください。本課題は「熟練エンジニアがソース全体を眺めて未熟・恥ずかしいと感じた箇所」を整理したコード品質改善タスクであり、正確性・保守性・一貫性を段階的に向上させることを目的とします。

## 2. 背景・前提条件 (Context)

`org-toolkit` は Emacs org-mode を TypeScript でパース/変換/エクスポートするライブラリ。`npm test`（vitest）・`npm run typecheck`（tsc）は全て緑、`npx oxlint` も現状エラーなしだが、以下の点が未熟または設計不備。`src/` 全体と `tests/`、エクスポータ、プラグイン、CLI、agenda を対象とする。

### 現状発生している問題（優先度順）

**[A: 正確性バグ] インラインマークアップ解析が org-mode の境界ルールを無視している**
- `src/parser.ts:940` 付近の `parseInline` は `text.indexOf(marker, index + 1)` で最初に現れる同じ記号を終端とみなすだけ。org-mode では強調記号は前後が空白/句読点/行端で囲まれる必要がある。
- 実証: `parse("2 * 3 * 4")` が `2 ` + bold(` 3 `) + ` 4` に誤解析される（正しくは全てプレーンテキスト）。`parse("*a *b* c*")` も不正確。
- 算術の `*`、分数の `/`、変数の `_` などを含む普通の文章がすべて誤って装飾ノードになる。パーサとして致命的な正確性欠陥。現状テストが通るのは parse/stringify が「自己整合」しているだけで、org-mode 仕様に対して誤り。

**[B: 設計の匂い] AST ノードに非公開の隠しプロパティ（副作用チャネル）を付与している**
- `src/node-annotations.ts` が `Object.defineProperty` で `enumerable:false` の `__orgTimestampText` / `__orgPlanningLines` / `__orgBlankLinesAfter` をノードへ直接生やす。AST 型定義（`src/ast.ts`）にはこれらのフィールドが一切宣言されていないのに、パーサ→ストリンギファ間のラウンドトリップがこの隠し状態に暗黙依存している。
- 実証: `Object.getOwnPropertyNames(heading)` に `__orgPlanningLines` が含まれるが `JSON.stringify` では不可視（プレイグラウンドの AST 表示にも出ない）。型に現れない“マジック状態”であり、利用者が驚く脆弱設計。WeakMap または型に明示されたフィールドで表現すべき。

**[C: 設計の匂い] `transform.ts` の手書きディープクローンと `format.ts` の `structuredClone` の不一致**
- `src/transform.ts:42` の `cloneValue` は `Reflect.ownKeys` + ディスクリプタで自作した 30 行の再帰クローン。`src/format.ts:19` は標準の `structuredClone` を使用。同じ“AST 複製”目的で2方式が混在。手書きクローンは境界ケース（getter/setter、Symbol キー等）で `structuredClone` と挙動が異なり得る。原則 `structuredClone`（または統一した単一ヘルパ）に統一すべき。隠しプロパティが非 enumerable でも `structuredClone` は保持するため置換可能。

**[D: 設計の匂い] `format()` のタグ整列が文字列後処理（正規表現）で実装されている**
- `src/format.ts` は `stringify(ast)` で一旦文字列化した後、`alignHeadingTagsInLine`（`src/format.ts` の正規表現）で行単位にタグ位置を整列させる。見出しの body と tags は `stringifyHeading`（`src/stringifier.ts`）の時点で構造的にアクセス可能なのに、レンダリング後の文字列を正規表現で再パースする“stringly-typed”手法。
- `TAG_COLUMN = 77`（`src/format.ts:5`）がマジックナンバーで/org-mode の `org-tags-column` 既定値だが出典のコメントがない。整列ロジックは `stringifyHeading` 側に統合すべき。

**[E: 保守性] 大量の重複コード（DRY 違反）**
- `assertNever` が 6 箇所の同一コピー: `src/text.ts:80`, `src/stringifier.ts:338`, `src/traverse.ts:215`, `src/exporters/markdown.ts:373`, `src/exporters/html.ts:361`, `src/agenda.ts:250`。
- `pad2` が 2 箇所: `src/transform.ts:114`, `src/builders.ts:260`。
- `joinTopLevelChildren` が 3 箇所のほぼ同一コピー: `src/stringifier.ts:274`, `src/exporters/markdown.ts:272`, `src/exporters/html.ts:263`。
- `stripBlockBoundaryNewlines` が 2 箇所の同一コピー: `src/exporters/markdown.ts:345`, `src/exporters/html.ts:300`。
- 日付フォーマット（`YYYY-MM-DD` + `pad2`）が `text.ts`/`stringifier.ts`/`agenda.ts`/両エクスポータに断在。
- `src/agenda.ts` の `renderInlineText`/`renderInlineNodeText`（`src/agenda.ts` 付近）は `src/text.ts` の `getTextContent` とほぼ同じインライン描画を再実装。`getTextContent` を再利用すべき。

**[F: 堅牢性] CLI 引数解析が手書きで脆い**
- `src/cli.ts` の `parseCliArgs` は自前フラグ解析。未知の `-` 付き引数を `if (arg.startsWith("-")) { continue; }`（`src/cli.ts:143`）で黙って無視し、typo（例: `--hml`）をエラーにしない。
- `--html` と `--markdown` の同時指定時、if/else 順で html が勝つ暗黙の優先順位がありユーザに不可解。
- エントリ検出 `isDirectInvocation` が `process.argv[1]` のファイル名正規表現に依存（`cli.ts/js/cjs`）して脆い。
- `void main().then((exitCode) => { process.exit(exitCode); })`（`src/cli.ts:246`）に `.catch` がなく、`main()` の未補足リジェクションが unhandledRejection になる。公式パーサ（`parseArgs`）の採用を検討すべき。

**[G: デッドコード・不要な抽象】**
- `src/parser.ts:266` の `export class Parser` は `Parser.parse` が `parse` を呼ぶだけの互換ラッパー。「CLI milestone 用」とコメントにあるが実質不要なクラス。
- `src/agenda.ts:47` の `resolveAgendaFiles` は `return resolveOrgFiles(sources, cwd)` のみの無意味なラッパ。
- `src/exporters/markdown.ts:141` と `src/exporters/html.ts:127,150` の `renderParagraph`（と html 側の一部）は `context` 引数を受け取って `void context` で捨てる未使用パラメータ。
- `src/exporters/markdown.ts` の `renderDocumentMetadata`（`:104`）は通常パス（`renderRoot` は frontmatter を使う）では到達不能。`html.ts` は `renderRoot` でメタデータを `<meta>` 化するのに markdown は frontmatter のみ、と一貫性がない。
- `src/agenda.ts:181` の `formatTodoTitle` が `heading.todoKeyword ?? "TODO"` とハードコード。`runAgenda` は `findTodos`（todoKeyword === "TODO" のみ）から収集するためこの `?? "TODO"` フォールバックは実質デッド。

**[H: 型安全性の匂い] `resolveTodos` プラグインが `as MutableHeading` で readonly を剥がして破壊的更新】**
- `src/plugins/resolveTodos.ts:5,24` が `-readonly` マッピング型で `as MutableHeading` キャストし、クローン上とはいえ `mutableHeading.todoKeyword = "DONE"` で書き換える。AST は `readonly` 指定の不変設計（copilot-instructions の Immutability 方針）だが、キャストで型保証を迂回している。プラグインは新しいノードを構築して返す純粋な形が望ましい。

**[I: ツールング] oxlint が実質未使用】**
- `package.json` に `oxlint` が devDependency にあるが `lint` スクリプトがなく、oxlint 設定ファイル（`.oxlintrc*`）も存在せず、`.github/workflows/ci.yml` にも lint ステップがない。依存だけ入れて未活用。スクリプトと CI に組み込むか、不要なら削除すべき。

## 3. 解決すべきゴール (Goal & Objective)
優先度 A→I の順に対応する。既存のテスト（`parse/stringify` ラウンドトリップ等）を壊さないこと。ただし A は正確性向上のため既存の“自己整合”テストに影響する場合があり、その場合は org-mode 仕様に沿う形へテストも更新すること。

- [x] **A**: `parseInline` に org-mode の強調境界ルール（前後の空白/句読点/行端、対応する開閉ペアの整合）を実装し、`2 * 3 * 4` や `*a *b* c*` がプレーンテキストとして正しく解析されるようにする。境界ルールの単体テストを追加。
- [x] **B**: `node-annotations.ts` の隠しプロパティを廃止し、AST 型に明示フィールドを追加するか WeakMap に移行する。パーサ→ストリンギファのラウンドトリップが型安全かつ可視化できる形で保持されること。
- [x] **C**: `transform.ts` の `cloneValue` を `structuredClone`（または共通の単一クローンヘルパ）に置換し、`format.ts` と方式を統一する。
- [x] **D**: `format()` のタグ整列を `stringifyHeading` 側（構造アクセス）へ移行し、文字列後処理の正規表現を削除。`TAG_COLUMN` は意図と出典をコメント化または設定化。
- [x] **E**: `assertNever`/`pad2`/`joinTopLevelChildren`/`stripBlockBoundaryNewlines`/日付フォーマットを共通ユーティリティ（例: `src/internal/*.ts`）へ集約し、重複を削除。`agenda.ts` の `renderInlineText` を `getTextContent` 利用に置換。
- [x] **F**: CLI 引数解析を Node 標準 `util.parseArgs`（等）に移行し、未知フラグをエラー化、同時指定の挙動を明確化、`main()` のリジェクションを補足（`.catch`）。
- [x] **G**: `Parser` クラス、`resolveAgendaFiles` ラッパ、未使用 `context` 引数、markdown の到達不能 `renderDocumentMetadata`、`formatTodoTitle` の `?? "TODO"` を削除または整理。
- [x] **H**: `resolveTodos` を `as MutableHeading` キャストによる破壊的更新から、新しいノードを構築して返す純粋な形へリファクタ。
- [x] **I**: oxlint を `npm run lint` スクリプト + CI ステップに組み込むか、不要なら devDependency から削除。設定ファイルを整備。
- [x] 制約: 変更後 `npm test` / `npm run typecheck` / `npm run build` がすべて成功すること。公開 API（`src/index.ts` の export）の破壊的変更は README と changeset（`npm run changeset`）で明示。

## 4. 期待する成果物 (Output Format)
- 優先度ごとの修正コード一式（またはパッチ）。可能なら A〜I を個別のコミット/PR に分割。
- 各修正理由とアプローチの簡潔な解説（とくに A の正確性ルール根拠、B/C のクローン方式選定理由）。
- `npm test` / `npm run typecheck` / `npm run build` の実行結果。A については新規の境界ルール単体テスト結果。
- 破壊的変更がある場合は changeset と README 更新。
